# TASK 03 — временный WireGuard RU ↔ FR

Scope разработки: **LOCAL_BUILD**. Основание: отдельное поручение владельца
от 2026-11-04. Разрешены создание файлов и локальные проверки; SSH, установка,
изменения VPS, commit и push исполнителем запрещены. Этот документ не является
разрешением на запуск команд с `--apply` на VPS.

**УТВЕРЖДЕНО для этого теста:** обычный WireGuard, отдельный `wg-test` на RU/FR,
FR `45.15.128.138`, без воздействия на старый NL и production VPN.
RU Ubuntu 24.04, `wolffrog` с sudo и установленный wireguard-tools; FR новая
Ubuntu с `wolffrog`/sudo — входные данные владельца, не наблюдения исполнителя.
FR не объявляется новым production egress. D-01/D-19/D-20 и baseline RU → NL
не переписываются; literal IPv4 используется только в этом временном тесте.

**ПРОВЕРИТЬ:** версия Ubuntu FR, наличие python3, ip/ss, wg/wg-quick, ping,
поддержка WG ядром, маршруты, адреса, firewall обеих VPS и провайдера,
фактический публичный исходный IPv4 RU, UDP и ICMP, часы серверов.
**ОТКРЫТО:** production-использование FR; данная задача этого не решает.

## Точные эффекты после отдельного одобрения

Кандидаты: `10.203.254.0/30` (RU `.1`, FR `.2`), UDP `51983` на обеих VPS.
Это не утверждённый адресный план: preflight проверяет пересечение с IPv4
маршрутами **всех таблиц** и адресами интерфейсов. Default исключён из проверки
пересечений, иначе никакая подсеть не могла бы пройти. При конфликте выбрать
другую RFC1918 /30 или порт и согласовать значения до подготовки обеих VPS.
Проверка повторяется перед активацией; порт проверяется также перед FR UDP-пробой.

| Команда | Эффект на VPS |
|---|---|
| без `--apply` / `--dry-run` | Только план; без subprocess, файлов, ключей и сети; это не аудит VPS |
| `preflight --apply` | Чтение маршрутов/адресов/портов; без записи |
| `probe --apply` | FR: один временный UDP socket до 30 секунд; RU: один пакет и ожидание echo до 30 секунд |
| `prepare --apply` | `/run/vpn-task03` root:root 0700; `private.key`, `settings.json` 0600; печать только публичного ключа |
| `up --apply` | Снимок маршрутов/rules, время запуска, peer и конфиг 0600 в том же каталоге; создание `wg-test` |
| `handshake --apply` | Только чтение handshake, identity, маршрутов/rules |
| `packets --apply` | Три ICMP echo через `wg-test`; чтение RX/TX, handshake и маршрутов |
| `down --apply` | Удаление только принадлежащего тесту интерфейса; проверка исходных маршрутов/rules |
| `cleanup --apply` | То же плюс удаление только известных тестовых файлов; пустой каталог остаётся |

`wg-quick` получает `Table = off`, `AllowedIPs` только удалённый адрес `/32`,
MTU 1380. Назначение адреса `/30` создаёт только connected route тестовой сети
и local/broadcast routes ядра. Это ожидаемые временные маршруты, удаляемые
вместе с интерфейсом. Не добавляются default routes, policy rules, NAT,
forwarding, DNS, hooks, sysctl, PSK, службы или автозапуск. RU инициирует связь
на FR, keepalive 5 секунд действует только пока существует тестовый интерфейс.
FR узнаёт endpoint RU после аутентифицированного пакета.

Ключ генерируется `wg genkey` только на соответствующей VPS; umask 077,
файл 0600, root:root. Конфиг `wg-test.conf` **без приватного ключа**: ключ
загружается через `wg set ... private-key /run/vpn-task03/private.key`.
Все runtime-файлы остаются вне Git, исчезают после reboot; секрет не передаётся
аргументом командной строки, не печатается и не копируется между VPS.
Не выполнять `wg showconf`, `wg show ... dump`, `cat private.key`, трассировку
секретов или сохранение диагностики в репозитории. Скрипт не читает чужие WG-конфиги.

## 1. Подготовка владельцем

Перед любыми изменениями: отдельно одобрить перечисленные эффекты и значения
на RU/FR, создать snapshot обеих VPS средствами провайдера, проверить консоль
восстановления. Не работать параллельно с другими сетевыми администраторами.
Скрипт блокирует свои параллельные вызовы через flock inode `/run`; другие
утилиты этот advisory lock не соблюдают. Использовать проверенную копию кода,
не редактируемую одновременно с запуском root.

На обеих VPS проверить зависимости без установки; недостающая зависимость —
**BLOCKED**, конкретный prerequisite: её отдельная одобренная установка владельцем.
FR-версия Ubuntu и инструменты не считаются известными по одному названию VPS.

```bash
python3 --version
command -v ip ss wg wg-quick ping
cat /etc/os-release
uname -r
python3 scripts/03_wg_test.py --help
python3 scripts/03_wg_test.py prepare --role ru --dry-run
sudo python3 scripts/03_wg_test.py preflight --role ru --apply
```

На FR заменить `--role ru` на `--role fr`. Если выбран иной порт/подсеть,
добавлять одинаковые `--port N --subnet X.X.X.X/30` **ко всем командам** обеих VPS.
Наличие другого `wg-test` останавливает подготовку; его автоматически не удалять.

Владелец просматривает на каждой VPS действующий firewall локально, без экспорта
дампов в Git/чат: `sudo nft list ruleset`, `sudo ufw status verbose`,
при использовании legacy iptables также `sudo iptables-save` и `sudo ip6tables-save`.
Отсутствие утилиты или одной цепочки не означает отсутствие firewall.
В панели провайдера отдельно проверить security groups/ACL.
Нужны RU outbound UDP к FR:51983 и ответы; FR inbound UDP:51983 от фактического
RU IPv4 и ответы; INPUT/OUTPUT ICMP между тестовыми адресами через wg-test.
FORWARD и NAT для этого теста не нужны. Просмотреть существующие широкие правила
forwarding: новый интерфейс не должен непреднамеренно попадать под production policy.
Если требуется изменить правила, **BLOCKED** до отдельного одобрения конкретной
правки с backup/rollback; скрипт firewall не меняет и не объявляет его безопасным.

## 2. Проверка UDP до активации WG

После ревью firewall, сначала FR (подставить реальный публичный исходный RU IPv4):

```bash
sudo python3 scripts/03_wg_test.py probe --role fr --ru-ip RU_PUBLIC_IPV4 --firewall-reviewed --apply
```

В течение 30 секунд на RU:

```bash
sudo python3 scripts/03_wg_test.py probe --role ru --firewall-reviewed --apply
```

Проверка одноразовая: FR отвечает только пакету фиксированного размера/префикса
от указанного RU IPv4, ответ не больше запроса; RU сверяет случайный nonce.
Это не криптографическая аутентификация и не постоянный echo-сервис. Дождаться
выхода обоих процессов и PASS на RU. Timeout/ошибка — **BLOCKED**, prerequisite:
подтверждённая двусторонняя UDP-доступность выбранного FR порта. Не использовать
`nc -zu` как доказательство. Успех echo ещё не доказывает прохождение WireGuard:
фильтрация протокола может отличаться; это выясняет реальный handshake ниже.

## 3. Генерация ключей и обмен

На соответствующих серверах после preflight:

```bash
sudo python3 scripts/03_wg_test.py prepare --role fr --apply
sudo python3 scripts/03_wg_test.py prepare --role ru --apply
```

Повтор до активации сохраняет ключ, проверяет параметры и снова выводит public key.
Передать **только вывод PUBLIC KEY**, сверив принадлежность RU/FR по доверенному
административному каналу. Копировать приватный файл не нужно. Доступ владельца
к VPS — только с проверенными SSH host keys; Codex SSH не выполняет.
Base64 public key сам по себе не удостоверяет сервер, нужна сверка источника.

## 4. Активация — отдельно от подготовки

Флаги ниже — утверждение оператора о выполненных проверках, не обход согласования.
Сначала FR, затем RU; в кавычках подставить public key противоположного сервера:

```bash
sudo python3 scripts/03_wg_test.py up --role fr --peer-key 'RU_PUBLIC_KEY' --firewall-reviewed --udp-verified --apply
sudo python3 scripts/03_wg_test.py up --role ru --peer-key 'FR_PUBLIC_KEY' --firewall-reviewed --udp-verified --apply
```

Повторный up при своей активной identity/том же peer сохраняет интерфейс и
проверяет маршруты; не сбрасывает timestamp. Ошибка при активации вызывает
попытку удаления созданного интерфейса; файлы остаются для контролируемого отката.
Сообщение ACTIVE **не означает** handshake. Подождать несколько секунд, не менять
firewall автоматически, не запускать следующий production этап.

## 5. Handshake и передача пакетов — разные проверки

На RU, затем FR:

```bash
sudo python3 scripts/03_wg_test.py handshake --role ru --apply
sudo python3 scripts/03_wg_test.py packets --role ru --apply
```

На FR использовать `--role fr`. Handshake должен быть ненулевым, не раньше
текущей активации, не в будущем и не старше 180 секунд по локальным часам.
При отсутствии handshake проверить корректность public keys, UDP, endpoint,
firewall и часы; наличие интерфейса не заменяет эту проверку.

`packets` требует 3/3 echo replies, реальный маршрут к peer через wg-test,
увеличение обоих счётчиков RX/TX и свежий handshake. Повторить на **обеих** VPS:
один PASS не закрывает двусторонний тест. Счётчики сами по себе могут расти
от keepalive, поэтому без успешных ping результат не принимается.
Все исходные маршруты IPv4/IPv6 всех таблиц и policy rules сравниваются со снимком
до up, исключая только маршруты самого wg-test. Это включает основной default.
При динамической смене маршрута проверка может остановиться даже без вины теста;
никакого автоматического восстановления общего routing state нет.

## 6. Удаление и откат

На каждой VPS (на FR заменить роль):

```bash
sudo python3 scripts/03_wg_test.py down --role ru --apply
sudo python3 scripts/03_wg_test.py cleanup --role ru --apply
```

`down` удаляет только wg-test с меткой теста и совпадающим локальным public key;
остальные интерфейсы не затрагивает. Повторное удаление безопасно. `cleanup`
удаляет runtime-файлы только после проверки маршрутов и известных имён/прав.
Сбой сверки маршрутов не препятствует удалению своего интерфейса, но оставляет
снимок и файлы для анализа. Не восстанавливать маршруты массово из снимка.
Не выполнять рекурсивное удаление `/etc/wireguard` или `/run`.

SIGKILL/потеря питания между системными командами не позволяют гарантировать
автоматический откат. Если identity/метка ещё не установлена или изменена,
скрипт откажется удалять интерфейс: владелец через консоль сверяет момент создания,
адреса и принадлежность wg-test; только после подтверждения разрешено адресное
`sudo ip link delete dev wg-test`. Проверить маршруты относительно исходного
снимка и затем cleanup. При частичной подготовке cleanup удаляет также известные
`.new` файлы. Reboot убирает runtime-state и интерфейс, но не предлагается как
штатный откат из-за воздействия на остальные сервисы. Удаление файла не является
гарантированным криптографическим стиранием памяти/swap/snapshot провайдера.

## Приёмка и локальная проверка

Это только транспортный тест; он не закрывает этап 3 ACCEPTANCE.md (PBR,
fail-closed, egress, DNS, клиентские тесты и миграция остаются отдельными задачами).

| Проверка | Ожидаемый результат | Фактический результат VPS |
|---|---|---|
| Preflight RU/FR и ревью firewall | Нет конфликтов, разрешён тестовый обмен | НЕ ВЫПОЛНЕНО |
| UDP probe | RU получил точный echo от FR | НЕ ВЫПОЛНЕНО |
| Handshake RU и FR | Свежий для текущей активации | НЕ ВЫПОЛНЕНО |
| Пакеты RU→FR и FR→RU | 3/3 в каждом направлении, RX/TX растут | НЕ ВЫПОЛНЕНО |
| Маршруты/rules | Исходные сохранены до/после и после down | НЕ ВЫПОЛНЕНО |
| Cleanup | Нет wg-test, нет runtime-секретов | НЕ ВЫПОЛНЕНО |

Протокол владельца вне Git: дата UTC, роли/версии, выбранные параметры,
согласовавший, PASS/FAIL/BLOCKED по каждой строке, timestamps handshake,
дельты RX/TX и результат rollback; без ключей, конфигов и диагностических дампов.

Локально: `python scripts/03_wg_test_checks.py` — проверки валидатора /30,
пересечений, свежести handshake, dry-run, gates, ошибок без секретов,
защиты чужого интерфейса, изменений маршрутов и критериев пакетов с mocks.
Они не запускают WG, sudo, SSH, sockets, установку или изменения ОС.
Синтаксис можно проверить через `ast.parse` без создания `__pycache__`.
Наблюдалось локально 2026-11-04 (Windows, Python 3.14.6): 11 тестов PASS,
`ast.parse` обоих скриптов PASS, проверка trailing whitespace PASS,
явный `up --role fr --dry-run` вывел только план. В тестах также проверены
откат при ошибке активации и отсутствие записей при повторном up.
Проверка настоящего ядра Linux, firewall, wg-quick и сети остаётся **BLOCKED**
до отдельного разрешения владельца на точные операции выше.

Следующее действие: ревью владельцем этого набора и точного плана теста RU/FR.
