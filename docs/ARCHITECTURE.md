# ARCHITECTURE — целевая техническая схема

Статус: проектное описание, **не подтверждённая конфигурация действующих серверов**. Все примерные значения требуют проверки аудитом. Основной нормативный документ — `SPEC.md`.

## 1. Топология

```text
                 [CLI / SSH]        [Telegram adapter, optional]
                      \                     /
                       [VPN Manager + SQLite]   (RU)
                                  |
[Devices] -- AmneziaWG --> [VPS RU: awg0, DNS, nftables/PBR, tc]
                                           |            \
                                RU public egress         WireGuard wg-nl
                                SNAT on RU               |
                                                 [VPS NL: wg-ru]
                                                         |
                                                   SNAT to NL IP
                                                         |
                                                     Internet

NL в переходный период: existing AmneziaVPN in Docker — не трогать.
NL в целевом production: только необходимый host-level WG, firewall/NAT, мониторинг и backup-приёмник; **старых AmneziaVPN-контейнеров нет**.
```

## 2. Логические адреса — ПРИМЕР, НЕ ПРИМЕНЯТЬ ДО АУДИТА

| Объект | Пример | Требует проверки |
|---|---|---|
| IPv4 клиента AWG | `10.80.0.0/24`, RU `10.80.0.1` | Нет ли пересечения с Docker, корпоративными сетями и существующим VPN NL |
| WG межсерверный | `10.90.0.0/30`, RU `.1`, NL `.2` | Тот же контроль конфликтов |
| Таблица PBR | `200 nl_egress` | Не занята ли таблица/правила |
| Физический интерфейс | `eth0` | Реальное имя на каждой VPS |
| Публичные endpoints | `RU_PUBLIC_IP` для клиентов; `nl-egress.internal` для WG на RU | Реальные адреса, доступность UDP и локальный resolver в `/etc/hosts` |

Клиентский IPv6 в MVP не выдаётся; не отключать IPv6 хоста без отдельного анализа зависимости существующих сервисов.

## 3. Путь исходящего пакета

1. Пакет приходит на `awg0` от выделенного клиенту `10.80.0.x`.
2. Для DNS и других явно разрешённых локальных служб RU — локальная доставка, не default-to-NL.
3. Предварительная проверка адресов назначения: запрещённые/специальные диапазоны и разрешённые локальные службы. Требуется перечень исключений для RFC1918, loopback, link-local, multicast и самой инфраструктуры.
4. Классификация в **prerouting**: `force_nl` имеет приоритет, далее разрешённые прямые RU, затем NL для прочих публичных адресов; отдельные ручные `force_ru` — после согласования семантики и конфликта с `force_nl`.
5. Выбранная метка сохраняется для существующего потока через conntrack. **Отдельно проверить** политику маркировки первых пакетов, восстановление метки, ICMP и поведение UDP.
6. `ip rule` направляет NL-маркированный поток в таблицу `nl_egress`, где default указывает на `wg-nl`, плюс стойкий `unreachable default` с худшим приоритетом. Отсутствие WG не должно приводить к возврату в main.
7. На RU трафик RU NAT-ится только при выходе через публичный RU-интерфейс. NL-пакеты отправляются по WG без SNAT на RU; исходные `10.80.0.x` видны на NL.
8. На NL маршрут обратно к `10.80.0.0/24` ведёт в `wg-ru`; в интернет NAT-ится только новая подсеть клиентов, прибывающая с `wg-ru`.
9. Форвардинг в обоих направлениях закрыт по умолчанию и разрешён только для ожидаемых интерфейсов, адресов и состояний соединений.

**Критическое требование:** правила в `forward` являются второй независимой защитой. Пакет с NL-назначением не может уйти в RU WAN ни при исчезновении интерфейса WG, ни при сбое маркера/правила, ни при рестарте менеджера. Применение этого утверждения доказывается тестами, не только обзором конфига.

## 4. Межсерверный WireGuard

- Отдельный host-level WG-интерфейс на NL. В переходный период **не** использовать и не менять существующий AmneziaVPN-контейнер; в конечной системе старого контейнера уже нет.
- Для RU принцип `Table=off` у `wg-quick` с управляемыми отдельно PBR-маршрутами; без автоматической подмены default route хоста.
- `AllowedIPs`: на RU допускает пересылку через NL назначений IPv4; на NL — конкретные клиентскую подсеть и WG-адрес RU. Эти значения не копировать без ревизии адресного плана.
- Роутинг endpoint NL всегда идёт через обычный RU WAN, чтобы не возникла рекурсия туннеля.
- Проверить фактический MTU и MSS при вложенной AWG+WG инкапсуляции и UDP.
- Доступность NL: health-check с реальным пробным внешним выходом через NL, а не только по `wg show`.
- На RU `Endpoint = nl-egress.internal:<port>` — **стабильное имя**, локально разрешаемое `/etc/hosts`. Использовать тестовую доменную метку только после проверки политики именования и локального resolver; не путать его с публичным именем RU для клиентов.
- При изменении `/etc/hosts` активный WireGuard не обязан сам обновить endpoint. Менеджер повторно разрешает имя и применяет новый endpoint к активному WG peer (`wg set ... endpoint ...`), затем проверяет реальный IPv4 выхода. Для автозапуска остаётся файл с hostname.
- Операция `vpnctl nl set-ip ...` — **запланированный CLI**, пока не реализован; она должна менять только управляемую запись `/etc/hosts`, обновлять активный peer и проверять результат. Нужны ограничения по роли, блокировка параллельных изменений, аудит и откат.
- При замене всей NL VPS воспроизводятся WG-конфиг, обратные маршруты, NAT, firewall, monitoring/backup. Ключ удалённого WG-сервера сохраняют безопасным способом или отдельно обновляют в конфигурации RU. Ключи клиентского AWG на РФ не меняются. См. `NL_ENDPOINT_RUNBOOK.md`.

## 5. DNS

- `dnsmasq` на RU, клиентам выдаётся адрес RU в AWG-сети.
- На старте один DNS-upstream/политика, без раздельного RU/NL DNS.
- Доступ к локальному DNS только из разрешённой VPN-сети (и локально по необходимости).
- Предупреждение: DNS-upstream RU может вернуть географически неидеальный CDN IP; обход DoH/DoT возможен. Не маскировать это как решённую задачу.

## 6. Списки и исключения

- Лёгкий fetcher раз в ~12 часов загружает географические RU-сети и списки исключений.
- Данные проходят санитарную проверку: формат CIDR, запрет bogon/служебных адресов в неверных категориях, размер, сравнение с предыдущим объёмом, проверка пересечений, учёт времени последнего успеха.
- Загрузка в nftables interval sets **атомарной заменой**; при сбое — предыдущая валидная версия.
- Источники блокировок/geo-IP и точные границы применения уточняются отдельно после проверки их качества. Оригинальная схема коллеги с BGP — источник идеи, не требование воспроизводить его стек.

## 7. Модель пользователей — человек прежде всего

```text
User(name unique case-insensitive: "Ivan")
  ├── Device(name: "iPhone", profile: "Ivan_iPhone", own AWG peer/IP/limits/traffic)
  ├── Device(name: "MacBook", profile: "Ivan_MacBook", own AWG peer/IP/limits/traffic)
  └── Device(name: "iPad", profile: "Ivan_iPad", own AWG peer/IP/limits/traffic)
```

- БД SQLite хранит пользователя с видимым точным именем, устройства с отдельными именами и связь `device→user` через внутреннюю ссылочную целостность. Внутренние ключи могут существовать, но не показываются в штатном UI.
- Не использовать Telegram ID/телефон/email в таблице пользователей или как идентификатор пира.
- `vpnctl user add Ivan`, `vpnctl device add Ivan iPhone` и аналогичные команды — **планируемый синтаксис**, не готовая исполняемая утилита.
- Схема БД и менеджер будут поддерживать уникальность имени пользователя по Unicode casefold и имя устройства внутри пользователя. Важно изучить коллизии Unicode (NFKC), длины, запрещённые символы пути и проблему `_` в составном имени; это открытое проектное решение.
- Имя файла для экспорта `Ivan_iPhone.conf`. Название туннеля внутри конкретного клиента подтверждается совместимостными тестами.
- Изменение названия устройства в менеджере не обязано автоматически переименовать уже импортированный клиентом туннель; это должно быть явно описано в UI.

## 8. VPN Manager, CLI, Telegram

- Одна кодовая база Python + SQLite, менеджер как библиотека/локальный сервис; CLI — независимый обязательный способ управления.
- AWG key/peer adapter применяет изменения к работающему интерфейсу и к конфигурации для восстановления после reboot, с проверкой согласованности и транзакционным журналом.
- `tc` adapter на RU: ограничения скорости по профилю с учётом направлений. Точные qdisc/IFB/filters выбрать по проверке на тестовой машине; **не считать достаточным простое правило по IP без теста download/upload**.
- Telegram-бот запускается отдельно и может останавливаться без воздействия на dataplane. Доступ к менеджеру через защищённый локальный интерфейс; никаких общедоступных административных API.
- Отдельное Telegram auth-хранилище содержит только то, что технически необходимо для проверки администратора/приглашений и привязки разрешённого самообслуживания; VPN-таблицы независимы. Роли Owner/Admin/User; приглашение однократное и одобрение администратором обязательно.
- Новые пользователи без Telegram создаются вручную администратором через CLI/бота, получают конфиги через контролируемую выдачу.

## 9. Мониторинг

- На RU периодическая запись счётчиков AWG по peer и системных метрик; на NL — ограниченный локальный агент или SSH/WG-поллинг **после** выбора безопасного механизма.
- По каждому профилю — байты/производные скорости; по пользователю — сумма профилей; по серверам — CPU/RAM/disks/сетевые счётчики.
- Для RU/NL отдельно нужны counters по направлению выхода; обычный счётчик peer их не различает.
- Временные ряды в SQLite с агрегацией. PNG-графики по запросу и уведомления от бота; при недоступности Telegram события не теряются.
- Для обнаружения полной потери RU нужен внешний наблюдатель (на NL или вне обеих VPS); сам бот на упавшей RU не отправит сообщение.

## 10. Этапы жизни NL (переходный и целевой)

**Внедрение:** провести read-only аудит AmneziaVPN/Docker, compose/containers, интерфейсов, iptables/nftables, NAT, `ip rule`, маршрутов, портов и ресурсов. Новый WG/маршруты внедрять без нарушения старых сервисов, по отдельному разрешению с rollback.

**Production:** после приёмки новой системы старую AmneziaVPN и Docker-контейнеры, принадлежащие этой установке, полностью удаляем отдельным утверждённым этапом с проверкой, что другие сервисы не используют Docker. Затем удаляем только подтверждённо устаревшие сети, тома, правила, пакеты и службы. Не предполагать, что удаление Docker глобально безопасно до аудита. См. `NL_MIGRATION.md`.

## 10.1. Меры защиты действующего NL сервиса до миграции

До изменений получить read-only снимок Docker networking, compose/containers, interfaces, iptables/nftables, NAT, `ip rule`, маршрутов, слушающих портов, conntrack и текущего использования ресурсов. Не копировать секреты и полные конфигурации в отчёт. Новые правила применять адресно, после бэкапа и с безопасным откатом. Отсутствие пересечения IP-адресаций/портов **не гарантирует** отсутствие конфликтов firewall; проверить docker chains и UFW.

## 10.2. Защита от подмены адреса NL

Локальный `/etc/hosts` управляет только адресом выбранного endpoint, но **не** является аутентификацией. WireGuard проверяет криптографический ключ удалённого пира; на новой VPS нужно обеспечить совпадение ожидаемого ключа либо согласованную замену. Следить, чтобы hostname не был использован в других unrelated конфигурациях. Подмена DNS/hosts на RU или ошибочная ручная запись может вызвать отказ, но не должна давать выход NL-трафика через RU.

## 11. Запрещено на этом этапе

- Автоматически генерировать production-секреты или запускать установку из одной общей постановки задачи.
- Утверждать, что Docker не нужен для конкретной версии AWG до проверки драйвера/пакетов.
- Утверждать, что Work имеет SSH-доступ, пока это не проверено в его среде.
- Превращать мониторинг или Telegram в единственную управляющую инфраструктуру.
- Применять демонстрационные адреса, правила и sysctl к работающему NL без аудита.
