# ARCHITECTURE — целевая техническая схема

Статус: целевая архитектура проекта. TASK 06 host-level transport развёрнут; клиентская часть и egress ещё не развёрнуты. Примерные значения требуют проверки аудитом. Основной нормативный документ — `SPEC.md`.

## 1. Топология

```text
[клиенты] -- AmneziaWG --> [RU 218852: VPN Manager, DNS, PBR/nftables, tc]
                                 |                          |
                       RU IPv4 direct             [изолированный межсерверный
                       SNAT (RU сети)              туннель: AWG — кандидат]
                                                            |
                                                [FR hiplet-142983: отдельный egress]
                                                            |
                                                     SNAT -> Internet

На FR независимо работает production Docker-контейнер amnezia-awg2 (UDP 40905).
Его не выводим из эксплуатации и не используем автоматически как новый peer.
```

Основной зарубежный узел — кандидат FR, а не NL. Роль FR production egress требует испытаний и утверждения; замена зарубежного узла не меняет клиентские AWG-профили.

## 2. Логические адреса — кандидаты, НЕ утверждённая настройка

| Объект | Значение | Статус |
|---|---|---|
| RU | `218852` (`218852.ru`), `137.22.146.212`, WAN `eth0` | наблюдалось в read-only аудите |
| FR | `hiplet-142983`, `45.15.128.138`, WAN `ens3` | наблюдалось в read-only аудите |
| Клиенты AWG | пример `10.80.0.0/24` | ПРОВЕРИТЬ против всех сетей |
| Межсерверная подсеть | пример `10.90.0.0/30` | ПРОВЕРИТЬ Docker/FR namespace |
| PBR table | пример `200 egress` | ПРОВЕРИТЬ идентификаторы и priority |
| Interserver UDP | НЕ ВЫБРАН; `40905` зарезервирован существующим FR VPN | ПРОВЕРИТЬ firewall провайдера |
| Endpoint hostname | НЕ ВЫБРАН | ПРОВЕРИТЬ модель переключения и резолвер |

На RU `ip_forward=0` до старта dataplane — допустимое текущее состояние. IPv6 хостов не отключать; клиентский IPv6 и DNS-leak тестировать отдельно.

## 3. Путь исходящего пакета

1. Пакет приходит на `awg0` от выделенного клиенту `10.80.0.x`.
2. Для DNS и других явно разрешённых локальных служб RU — локальная доставка, не default-to-egress.
3. Предварительная проверка адресов назначения: запрещённые/специальные диапазоны и разрешённые локальные службы. Требуется перечень исключений для RFC1918, loopback, link-local, multicast и самой инфраструктуры.
4. Классификация в **prerouting**: `force_egress` имеет приоритет, далее разрешённые прямые RU, затем egress для прочих публичных адресов; отдельные ручные `force_ru` — после согласования семантики и конфликта с `force_egress`.
5. Выбранная метка сохраняется для существующего потока через conntrack. **Отдельно проверить** политику маркировки первых пакетов, восстановление метки, ICMP и поведение UDP.
6. `ip rule` направляет egress-маркированный поток в таблицу `egress`, где default указывает на `<interserver_iface>`, плюс стойкий `unreachable default` с худшим приоритетом. Отсутствие межсерверного интерфейса не должно приводить к возврату в main.
7. На RU трафик RU NAT-ится только при выходе через публичный RU-интерфейс. egress-пакеты отправляются по WG без SNAT на RU; исходные `10.80.0.x` видны на зарубежном узле.
8. На выбранном зарубежном узле обратный маршрут к `10.80.0.0/24` ведёт в `<interserver_iface_fr>`; в интернет NAT-ится только новая подсеть клиентов, прибывающая с `<interserver_iface_fr>`.
9. Форвардинг в обоих направлениях закрыт по умолчанию и разрешён только для ожидаемых интерфейсов, адресов и состояний соединений.

**Критическое требование:** правила в `forward` являются второй независимой защитой. Пакет с зарубежным назначением не может уйти в RU WAN ни при исчезновении интерфейса WG, ни при сбое маркера/правила, ни при рестарте менеджера. Применение этого утверждения доказывается тестами, не только обзором конфига.

## 4. Межсерверный транспорт — TASK 06 host transport активен

- Обычный WireGuard RU↔FR тестировался в ноябре 2026: кратковременный handshake и ICMP сменились отсутствием устойчивого обмена. Испытание **не пройдено**; причина (включая возможную фильтрацию) не доказана.
- Обычный WireGuard не возвращается как транспорт: предыдущий тест был нестабилен.
- Для межсерверного транспорта выбран userspace `amneziawg-go`; владелец принял TASK 05 по свежему handshake и двустороннему 1024-байтовому UDP/TCP echo на RU/FR. Тест использовал отдельные временные ключи, `awg-test`, `10.203.254.0/30`, UDP `51983`, MTU `1280`; cleanup прошёл на обоих узлах.
- На FR nftables INPUT hook обнаружено правило DROP для всех типов ICMP без ограничения интерфейса. Счётчик вырос на четыре пакета во время четырёх RU→FR ping; захват на `awg-test` видел запросы, но не ответы. FR→RU ping прошёл 4/4. Firewall не менялся; ICMP не является критерием транспортного smoke.
- Постоянный интерфейс `awg-transport` использует userspace `amneziawg-go` и отдельный `awg`, с UAPI socket `/run/vpn-task06/amneziawg`, /30 `10.203.254.0/30`, UDP 51983, MTU 1280 и только peer `/32`. Отдельные systemd units обеспечивают автозапуск, ограниченный restart, interface-bound echo probe и read-only monitor timer.
- Короткий TASK 06 smoke подтвердил свежий handshake и двусторонний TCP/UDP echo до и после рестарта только RU unit и только FR unit; systemd units/timer включены. SSH и host network baseline остались доступны/неизменны.
- FR `amnezia-awg2` оставался запущен, UDP 40905 опубликован; Docker, сети и конфигурация production VPN не менялись. Проверка клиентского data plane production VPN не проводилась. Не модифицировать этот сервис и Docker сеть.
- Не проверялись 15-минутная нагрузка, reboot, production client data plane или использование туннеля для клиентского egress. Постоянный host tunnel сам по себе не включает PBR/NAT/DNS.
- Не менять default route управляющих хостов; PBR только для клиентского трафика. Отдельные статические/маршрутные инварианты для endpoint и management SSH. Удалённый peer криптографически аутентифицируется, hostname — не идентичность.
- Схема `Table=off`, AllowedIPs, возвратный маршрут, NAT и kill-switch зависит от итогового транспорта и проверяется до применения. Фактические `MTU/MSS`, TCP/UDP и отсутствие утечек устанавливаются тестами.
- Постоянный host-level health-check проверяет свежий handshake + двустороннюю UDP/TCP передачу; ICMP на FR заблокирован общим INPUT DROP. Реальный egress IPv4 и длительную работу с периодами простоя/восстановления проверить отдельно перед использованием канала для клиентского egress.
- Замена FR на другую зарубежную VPS: безопасное переключение активного endpoint и доверенного peer, воспроизведение обратного маршрута/NAT/firewall/backup с подтверждением egress. Клиентские профили RU остаются неизменными. Конкретное имя CLI и способ резолвинга ещё не утверждены.

Конкретные units, pinning/hash, фактические измерения, ограничения, полномочия и
адресный rollback записаны в `TASK_06_PERMANENT_AWG_TUNNEL.md`.

## 5. DNS

- `dnsmasq` на RU, клиентам выдаётся адрес RU в AWG-сети.
- На старте один DNS-upstream/политика, без раздельного RU/egress DNS.
- Доступ к локальному DNS только из разрешённой VPN-сети (и локально по необходимости).
- Предупреждение: DNS-upstream RU может вернуть географически неидеальный CDN IP; обход DoH/DoT возможен. Не маскировать это как решённую задачу.

## 6. Списки и исключения

- Лёгкий fetcher раз в ~12 часов загружает географические RU-сети и списки исключений.
- Данные проходят санитарную проверку: формат CIDR, запрет bogon/служебных адресов в неверных категориях, размер, сравнение с предыдущим объёмом, проверка пересечений, учёт времени последнего успеха.
- Загрузка в nftables interval sets **атомарной заменой**; при сбое — предыдущая валидная версия.
- Источники блокировок/geo-IP и точные границы применения уточняются отдельно после проверки их качества. Оригинальная схема коллеги с BGP — источник идеи, не требование воспроизводить его стек.

## 7. Модель пользователей — человек прежде всего

```text
User(name unique case-insensitive: "Ivan")
  ├── Device(name: "iPhone", profile: "Ivan_iPhone", own AWG peer/IP/limits/traffic)
  ├── Device(name: "MacBook", profile: "Ivan_MacBook", own AWG peer/IP/limits/traffic)
  └── Device(name: "iPad", profile: "Ivan_iPad", own AWG peer/IP/limits/traffic)
```

- БД SQLite хранит пользователя с видимым точным именем, устройства с отдельными именами и связь `device→user` через внутреннюю ссылочную целостность. Внутренние ключи могут существовать, но не показываются в штатном UI.
- Не использовать Telegram ID/телефон/email в таблице пользователей или как идентификатор пира.
- `vpnctl user add Ivan`, `vpnctl device add Ivan iPhone` и аналогичные команды — **планируемый синтаксис**, не готовая исполняемая утилита.
- Схема БД и менеджер будут поддерживать уникальность имени пользователя по Unicode casefold и имя устройства внутри пользователя. Важно изучить коллизии Unicode (NFKC), длины, запрещённые символы пути и проблему `_` в составном имени; это открытое проектное решение.
- Имя файла для экспорта `Ivan_iPhone.conf`. Название туннеля внутри конкретного клиента подтверждается совместимостными тестами.
- Изменение названия устройства в менеджере не обязано автоматически переименовать уже импортированный клиентом туннель; это должно быть явно описано в UI.

## 8. VPN Manager, CLI, Telegram

- Одна кодовая база Python + SQLite, менеджер как библиотека/локальный сервис; CLI — независимый обязательный способ управления.
- AWG key/peer adapter применяет изменения к работающему интерфейсу и к конфигурации для восстановления после reboot, с проверкой согласованности и транзакционным журналом.
- `tc` adapter на RU: ограничения скорости по профилю с учётом направлений. Точные qdisc/IFB/filters выбрать по проверке на тестовой машине; **не считать достаточным простое правило по IP без теста download/upload**.
- Telegram-бот запускается отдельно и может останавливаться без воздействия на dataplane. Доступ к менеджеру через защищённый локальный интерфейс; никаких общедоступных административных API.
- Отдельное Telegram auth-хранилище содержит только то, что технически необходимо для проверки администратора/приглашений и привязки разрешённого самообслуживания; VPN-таблицы независимы. Роли Owner/Admin/User; приглашение однократное и одобрение администратором обязательно.
- Новые пользователи без Telegram создаются вручную администратором через CLI/бота, получают конфиги через контролируемую выдачу.

## 9. Мониторинг

- На RU периодическая запись счётчиков AWG по peer и системных метрик; на зарубежном узле — ограниченный локальный агент или SSH/WG-поллинг **после** выбора безопасного механизма.
- По каждому профилю — байты/производные скорости; по пользователю — сумма профилей; по серверам — CPU/RAM/disks/сетевые счётчики.
- Для RU/egress отдельно нужны counters по направлению выхода; обычный счётчик peer их не различает.
- Временные ряды в SQLite с агрегацией. PNG-графики по запросу и уведомления от бота; при недоступности Telegram события не теряются.
- Для обнаружения полной потери RU нужен внешний наблюдатель (на зарубежном узле или вне обеих VPS); сам бот на упавшей RU не отправит сообщение.

## 10. Сосуществование с FR production AmneziaVPN

FR `hiplet-142983`: Docker-контейнер `amnezia-awg2`, UDP 40905 — защищённый работающий сервис. **Нет требования миграции или удаления после запуска новой системы.**

Привилегированный read-only аудит Docker networking, действующих nftables/iptables/UFW цепочек, `amn0`, подсетей и NAT завершён и принят. Не собирать ключи, environment и полные VPN-конфиги. TASK 06 обновил live baseline, зафиксировал точечный memory sample сервиса и применил адресный rollback design. До клиентского egress остаются отдельная оценка нагрузки FR, reboot/recovery validation и доступный владельцу тест production VPN client data plane.

Демонстрация безопасности — реальный пользовательский тест production AmneziaVPN до и после каждого сетевого изменения. Даже отдельный namespace не гарантирует независимость от host firewall и routing.

## 10.1. Переключение зарубежного egress

Endpoint hostname (если выбран) не обеспечивает аутентификацию сам по себе. Изменение DNS/hosts не гарантирует обновления активного peer; механизм update зависит от одобренного транспорта. Невозможность переключения не должна приводить к выходу зарубежного клиентского трафика через RU WAN. Исторические `NL_ENDPOINT_RUNBOOK.md` и `NL_MIGRATION.md` **не применять**.
