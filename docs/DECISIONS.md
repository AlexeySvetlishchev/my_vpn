# DECISIONS — журнал архитектурных решений

Источник: согласования в текущей беседе. Эти решения нельзя менять ссылкой на «best practices» без отдельного согласования владельца.

| ID | Статус | Решение |
|---|---|---|
| D-01 | УТВЕРЖДЕНО | Две VPS: РФ и NL, Ubuntu 24.04 LTS, по 2 vCPU/4 ГБ RAM; диапазон 10–50 клиентов |
| D-02 | УТВЕРЖДЕНО | РФ VPS чистая. NL: AmneziaVPN в Docker сохраняем **только на период внедрения**; после приёмки production старая инсталляция полностью выводится из эксплуатации и удаляется отдельным согласованным этапом |
| D-03 | УТВЕРЖДЕНО | Клиентский вход — AmneziaWG; межсерверный транспорт — WireGuard |
| D-04 | УТВЕРЖДЕНО | RU IP напрямую, остальные публичные IPv4 через NL; ручные исключения через NL |
| D-05 | УТВЕРЖДЕНО | Fail-closed для NL, не делать fallback через RU |
| D-06 | УТВЕРЖДЕНО | Один DNS на RU, без клиентского IPv6 на первом этапе |
| D-07 | УТВЕРЖДЕНО | Лёгкая система, без обязательных тяжёлых сервисов BGP/Grafana и отдельной СУБД |
| D-08 | УТВЕРЖДЕНО | VPN Manager + обязательный CLI, Telegram — необязательный интерфейс, не источник истины |
| D-09 | УТВЕРЖДЕНО | Пользователь — имя администратора в неизменённом видимом виде; уникальность без учёта регистра |
| D-10 | УТВЕРЖДЕНО | Пользователь владеет несколькими независимыми VPN-профилями/устройствами |
| D-11 | УТВЕРЖДЕНО | Имя профиля/файла: `User_Device`, **подчёркивание**: `Ivan_iPhone.conf` |
| D-12 | УТВЕРЖДЕНО | Нет обязательных телефона/email/Telegram ID у VPN-пользователей |
| D-13 | УТВЕРЖДЕНО | Одноразовое приглашение → заявка → одобрение Admin для Telegram-самообслуживания |
| D-14 | УТВЕРЖДЕНО | Admin может создать VPN-пользователя и профиль вручную, в том числе без Telegram |
| D-15 | УТВЕРЖДЕНО | Лимиты скорости задаёт только Admin/Owner, персонально для профилей |
| D-16 | УТВЕРЖДЕНО | Telegram-дэшборд: графики по профилям/пользователям, серверная статистика, алерты |
| D-17 | УТВЕРЖДЕНО | Локальные резервные копии плюс зашифрованная копия на NL |
| D-18 | УТВЕРЖДЕНО | Утверждённый проект нельзя перепроектировать исполнителю без change request |
| D-19 | УТВЕРЖДЕНО | NL — сменяемый egress, смена публичного IPv4 и замена VPS без правки клиентских AWG-конфигураций |
| D-20 | УТВЕРЖДЕНО | Межсерверный WG endpoint на RU задаётся hostname (пример `nl-egress.internal`), который разрешается через управляемую запись `/etc/hosts` на RU |
| D-21 | УТВЕРЖДЕНО | При смене IP менеджер обновляет `/etc/hosts`, активный WG endpoint, проверяет egress, обеспечивает fail-closed и журнал изменений; `vpnctl nl set-ip` — запланированная CLI-команда |
| D-22 | УТВЕРЖДЕНО | Целевая NL не содержит старой AmneziaVPN/Docker; удаление только после приёмки новой системы и отдельного разрешения |

## Инженерные гипотезы, которые НЕ являются подтверждёнными решениями

| ID | Статус | Гипотеза / проверка |
|---|---|---|
| H-01 | ПРОВЕРИТЬ | Работа выбранной версии AmneziaWG без Docker на конкретном ядре Ubuntu 24.04 и в используемых клиентах |
| H-02 | ПРОВЕРИТЬ | nftables interval sets + policy routing + conntrack маркировка обеспечивают все edge-cases fail-closed |
| H-03 | ПРОВЕРИТЬ | Отдельный WG на NL без конфликтов с действующей AmneziaVPN/Docker firewall |
| H-04 | ПРОВЕРИТЬ | `tc` и при необходимости IFB обеспечивают надёжные download/upload ограничения на профиль |
| H-05 | ПРОВЕРИТЬ | Импорт AmneziaWG/AmneziaVPN сохраняет ожидаемое отображаемое название `Ivan_iPhone` |
| H-06 | ПРОВЕРИТЬ | Подход к статистике AWG + nftables сохраняет точность при рестартах и обновлениях |
| H-07 | ПРОВЕРИТЬ | Work в доступном пользовательском окружении реально способен выполнить SSH через согласованный механизм |
| H-08 | ПРОВЕРИТЬ | `getent` разрешает локальный NL hostname из `/etc/hosts` как задумано, `wg set` переприменяет новый endpoint без restart AWG, новые соединения восстанавливаются |
| H-09 | ПРОВЕРИТЬ | При смене / замене NL сохраняются NAT, обратный маршрут, ключ пира и fail-closed; автоматический rollback ограничен реальной доступностью прежнего endpoint |
| H-10 | ПРОВЕРИТЬ | После удаления старой NL AmneziaVPN/Docker не нарушается новый WG/firewall/backup; нет иных Docker-потребителей |

## Регламент change request

Предложение изменения оформляется отдельной записью: затронутые D/H/Q, текущая схема, предлагаемое изменение, зачем, альтернатива без изменения, риски безопасности/доступности, план миграции и отката, проверки и явное решение владельца (`APPROVED`/`REJECTED`). До `APPROVED` исходный baseline действует.
