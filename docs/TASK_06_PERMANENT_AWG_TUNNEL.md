# TASK 06 — постоянный межсерверный AmneziaWG RU ↔ FR

**Статус:** подготовлен к отдельному рассмотрению; ничего не установлено и не
активировано по TASK 06. Этот документ не является разрешением включать службу.
Клиентские VPN-профили, PBR, NAT, DNS и egress в scope не входят.

## 1. Основание и границы

TASK 05 принят владельцем как успешный короткий транспортный smoke: userspace
`amneziawg-go` установил handshake; 1024-байтовый TCP и UDP echo прошёл в обе
стороны; адресный cleanup завершился на RU и FR. На FR nftables INPUT drop
отбрасывает все ICMP без привязки к интерфейсу; firewall менять не требуется.

FR `hiplet-142983` продолжает содержать защищённый production Docker
`amnezia-awg2` на UDP 40905. Не останавливать/перезапускать контейнер, не читать
его полную конфигурацию/environment, не менять Docker networking, firewall,
global routes, sysctl или системные сетевые службы. Текущий TASK 06 проектирует
только отдельный host userspace AWG transport.

Один и тот же пользователь `wolffrog` сохраняется на обоих узлах. SSH-ключи
Codex `codex_ru` и `codex_fr` остаются раздельными; новые Unix-пользователи не
создаются. Право SSH или sudo не означает авторизацию для будущего включения
службы — перед активацией требуется отдельное явное разрешение владельца.

## 2. Предлагаемая конфигурация

| Параметр | План | Ограничение |
|---|---|---|
| Реализация | Закреплённые бинарники TASK 05: `amneziawg-go` + `awg` | Только userspace; kernel AWG не устанавливать/обновлять |
| Интерфейс | `awg-transport` | Не использовать `awg-test`; маркировать alias и проверять ifindex/тип перед любым удалением |
| Адреса | RU `10.203.254.1/30`, FR `10.203.254.2/30` | Повторно проверить маршруты и адреса непосредственно перед созданием |
| Порт | UDP 51983 на обоих узлах | FR production UDP 40905 зарезервирован и неприкосновенен; проверить текущую занятость 51983 |
| MTU | Начальное значение 1280 | Перепроверить TCP/UDP и фрагментацию; не менять MTU production-интерфейсов |
| AllowedIPs | Только адрес второго peer `/32` | Не принимать default route, клиентские подсети, `Table=auto` или маршруты пользователей |
| Параметры обфускации | Зафиксированный TASK 05 AWG2-compatible профиль | Использовать только пару новых ключей постоянного канала; не повторять тестовые ключи |
| Подъём | Явный systemd unit с enable/start только после отдельного approval | На этом подготовительном этапе unit не устанавливать и не включать |

Временные порт и подсеть TASK 05 прошли короткую проверку отсутствия конфликтов.
Перед постоянной установкой всё равно повторно проверить свежие адреса,
маршруты всех таблиц, интерфейсы, слушающие UDP сокеты и FR baseline
`docker0`/`amn0`. Если baseline изменён, 51983 занят, появился маршрут/адрес,
пересекающийся с `/30`, или endpoint RU↔FR уходит через новый интерфейс —
остановиться и пересогласовать значения.

## 3. Установка без побочных сетевых эффектов

1. Подготовить bundle из закреплённых исходников/бинарников TASK 05; проверить
   commit IDs, SHA-256 manifest и воспроизводимость хэшей. Никаких секретов в
   bundle/Git.
2. На обоих VPS сделать baseline перед установкой: SSH доступен; default route,
   все адреса/маршруты/rules, firewall hash, UDP 51983 и состояние systemd;
   на FR — безопасное состояние контейнера `amnezia-awg2`/UDP 40905 и сети
   `amn0`/`docker0`. Полные Docker inspect, Env и VPN-конфиги не читать.
3. Сгенерировать независимые ключи на RU/FR непосредственно на узлах. Хранить
   private keys только в root-owned каталоге `/etc/vpn-task06` с каталогом
   `0700`, файлами `0600`; обменять только public keys. Резервные копии ключей,
   если потребуются, зашифровать и хранить вне репозитория.
4. Установить только фиксированные `amneziawg-go`, `awg`, узкий launcher/helper,
   manifest и unit-файл. Не вызывать `awg-quick`/`wg-quick`, потому что они могут
   менять маршруты или firewall. Компоненты проверяют фиксированные пути,
   хэши, роль и права до любого действия.
5. До отдельной активации оставить unit disabled/stopped. `daemon-reload` и
   `enable --now` выполняются только в разрешённой части будущего TASK 06.

## 4. Постоянная служба, безопасное восстановление и мониторинг

- Один root-owned unit `vpn-task06-awg.service`, `After=network-online.target`,
  `WantedBy=multi-user.target`. Использовать только фиксированный launcher без
  `shell=True`, `eval`, произвольных аргументов, environment secrets или
  конфигов из writable-путей.
- При запуске создать только `awg-transport`, установить alias
  `vpn-task06:<instance-id>`, сверить ifindex и тип интерфейса, назначить
  `/30`, MTU и один peer `/32`; default route и host-wide routing не трогать.
- Ограничить автоматические рестарты: `Restart=on-failure`, задержка и
  `StartLimitBurst`; на FR сначала измерить CPU/RAM запущенного userspace peer.
  Не применять неподтверждённые лимиты, способные затронуть production.
- Stop/recovery helper останавливает только PID/cgroup своего unit. Удаляет
  интерфейс лишь при совпадении точного имени, alias, ifindex, link type и
  локального ownership ledger. При foreign/mismatched объекте — fail closed,
  сигнал оператору, без `ip link delete`.
- Мониторинг лёгкий: systemd timer или встроенная проверка свежести handshake,
  роста peer RX/TX при TCP/UDP echo, состояния unit и наличия адресного
  connected route. Пинг не критерий здоровья из-за FR INPUT ICMP DROP.
  Мониторинг read-only: при деградации сообщает/алертит, но не меняет firewall,
  маршруты и не перезапускает production VPN.
- Не добавлять внешние monitoring stack, Docker, PBR/NAT/DNS или клиентские
  маршруты в TASK 06.

## 5. Проверки после отдельно разрешённой активации

1. `systemctl is-enabled/is-active vpn-task06-awg.service`; проверить свежий
   handshake и UDP/TCP payload в обоих направлениях через `awg-transport`.
2. Сравнить RU/FR default routes, все остальные маршруты и адреса, правила и
   firewall с baseline; убедиться, что SSH продолжает работать и тестовый
   endpoint не маршрутизируется в туннель.
3. На FR read-only проверить, что `amnezia-awg2` остаётся running и UDP 40905
   опубликован; владелец отдельно проводит реальный клиентский тест production
   AmneziaVPN до и после сетевого этапа. Container running сам по себе не
   подтверждает client data plane.
4. Проверить остановку/запуск только TASK 06 unit, восстановление при падении
   userspace процесса, отказ handshake и reboot/autostart в согласованное окно.
   Повторная активация обязана сохранять ownership checks и не удалять foreign
   interfaces.
5. Выполнить согласованный короткий stability run; 15-минутный TASK 05 тест не
   проводился. Замерить CPU/RAM FR, handshake age, RTT, потери и TCP/UDP echo.
   Не переходить к клиентскому трафику до отдельного решения.

## 6. Резервирование и адресный откат

До изменений сохранить root-only резервные копии только создаваемых/заменяемых
TASK 06 unit/helper/config/ sudoers файлов с SHA-256 и владельцем/режимом.
Не копировать Docker конфиги или полные production VPN конфиги. План отката:

1. Остановить и отключить только `vpn-task06-awg.service` через фиксированный
   TASK 06 helper.
2. Завершить только его cgroup/PID; удалить `awg-transport` лишь после проверки
   alias + ifindex + link type + ledger. При несовпадении остановиться.
3. Убедиться, что interface, unit и runtime state TASK 06 отсутствуют; сравнить
   default route, прочие адреса/маршруты, firewall и SSH с baseline.
4. Удалить/восстановить только TASK 06 файлы из зафиксированного backup,
   запустить `systemctl daemon-reload`, проверить, что FR production container
   не изменён. Не выполнять общий flush/cleanup и не менять чужие файлы.

Откат не должен редактировать `/etc/docker`, FR Docker networks, nftables/
iptables/UFW, sysctl, `/etc/hosts`, host default routes или другие сервисы.

## 7. Полномочия и отзыв доступа

Сохранить `wolffrog` и отдельные Codex SSH ключи. Для будущего этапа предпочтителен
fixed-purpose root helper с точными действиями и неизменяемыми путями; не
предоставлять постоянный `NOPASSWD: ALL`, shell или произвольный Python root.
Sudoers TASK 06 ограничить точными командами launcher и минимальным stdin для
public peer key. Быстрый отзыв: удалить только `/etc/sudoers.d/vpn-task06`,
проверить `visudo -c`, закрыть Codex SSH sessions и удалить соответствующие
Codex public keys из `authorized_keys`, не затрагивая ключи владельца; service
должен продолжать работать независимо от Codex SSH access. Точный механизм
активации/владения одобряется вместе с конкретным планом внедрения.
