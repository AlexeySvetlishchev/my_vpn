# SECURITY — модель угроз и ограничения

## 1. Инварианты

1. **Нет утечки зарубежного клиентского трафика через RU.** При отказе межсерверного туннеля разрешены только прямые RU-направления, которые действительно определены как RU; всё назначенное зарубежному egress — fail-closed.
2. **Действующий AmneziaVPN FR (`hiplet-142983`, `amnezia-awg2`, UDP 40905) защищён бессрочно**, до отдельного явного решения владельца. Нет планового удаления Docker/VPN после запуска новой системы. Сетевые изменения требуют baseline, проверки с реального VPN-клиента и адресного rollback.

TASK 05 подтвердил отдельный userspace AmneziaWG transport коротким тестовым handshake и двусторонним TCP/UDP echo. FR nftables INPUT отбрасывает ICMP на всех интерфейсах; не ослаблять это правило ради ping. Пользоваться TCP/UDP тестовой проверкой либо получать отдельное согласование на строго ограниченное правило. TASK 05 helper не читает Docker metadata; его baseline check не подтверждает здоровье production VPN.
TASK 06 запустил отдельный userspace service `awg-transport` под systemd с новым
отдельным ключом на каждом сервере (private key root-only `/etc/vpn-task06`,
0600). Ключи не передавались в отчёт, локальный репозиторий или Git. Helper
проверяет принадлежность интерфейса через alias, ifindex, link type и локальный
ledger; cleanup fail-closed. Baseline-сравнение маскирует только изменяемые
счётчики/времена жизни, сохраняя порядок firewall rules. Мониторинг только читает
состояние/обменивается тестовым payload и не меняет firewall/routes/production.
Task-level service работает независимо от Codex SSH; новые sudoers/учётные
записи не создавались. FR container running и UDP publication проверены, но
production client data plane отдельно не тестировался.

3. **Telegram не является доверенным идентификатором VPN-пользователя.** В основной модели VPN — только имена людей и их устройства, без Telegram ID/телефонов.
4. **Telegram является внешним, потенциально ненадёжным административным интерфейсом.** Для допуска к командам требуются технические ID отправителей в отдельном защищённом auth-хранилище бота. Нет Telegram — CLI продолжает работать.
5. **Ключи и секреты не публикуются в чате, git, бэкап-логах и диагностике.**

## 2. Роли и полномочия

| Операция | Owner | Admin | Approved User | Неизвестный |
|---|---|---|---|---|
| Создать/отозвать приглашение | Да | Да | Нет | Нет |
| Одобрить заявку | Да | Да | Нет | Нет |
| Создать пользователя вручную | Да | Да | Нет | Нет |
| Создать/заблокировать устройство другого человека | Да | Да | Нет | Нет |
| Поменять скорость | Да | Да | Нет | Нет |
| Посмотреть все графики и алерты | Да | Да | Нет | Нет |
| Посмотреть свои разрешённые устройства | Да | Да | Да | Нет |
| Назначать/снимать Admin | Да | Нет | Нет | Нет |

RBAC-проверка на **каждом** вызове, включая старые inline callback-и. Для людей без Telegram самообслуживание в Telegram отсутствует; администратор делает операции за них.

## 3. Закрытое приглашение

- Приглашение — случайный криптографический токен, одноразовый, со сроком действия и отзываемый.
- В БД хранится только хэш токена; использование атомарно, гонки должны приводить не более чем к одной принятой заявке.
- Открытие ссылки **не** создаёт VPN-пир или доступ к статистике.
- Одобрение администратором обязательно, включая случаи передачи приглашения другому человеку.
- При первичном самообслуживании бот создаёт отдельную минимальную запись привязки в auth-слое, не в таблице VPN-пользователей.
- Rate limiting; отсутствие раскрытия информации в ответе неавторизованному; журналирование важных событий без секретов.

## 4. Разделение полномочий процессов

- Telegram-процесс без root, без прямых полномочий на firewall и управление ключами.
- VPN Manager/CLI осуществляет авторизованные операции через локальный интерфейс с проверкой роли; root-only helper — только для минимального белого списка операций.
- Никаких удалённо доступных административных TCP-портов без отдельного согласования.
- `sudoers` и systemd capabilities минимальны; не использовать широкую команду shell как общий API из Telegram.
- CLI через SSH должен работать независимо от Telegram.

## 5. Конфигурации и ключи

- Один peer на устройство, ключи уникальны; отзыв peer разрывает доступ соответствующего профиля.
- Передача файла `.conf` в Telegram несёт риск, так как переписка с ботом не является end-to-end секретным каналом. Для production предпочесть одноразовую защищённую выдачу или контролируемую передачу администратором.
- При автоматической генерации хранить публичный ключ, адрес и метаданные; решение об обращении с приватным ключом и повторной выдаче должно быть отдельно утверждено.
- Логи не должны содержать приватные ключи, токен бота, токены приглашений, одноразовые download URL и секреты резервного копирования.

## 6. Сеть и отказоустойчивость

- Разделить `input`, `forward`, `postrouting`; строгая anti-spoofing фильтрация исходных IP AWG-пиров.
- Защитить путь до публичных межсерверных endpoints, чтобы межсерверный туннель не маршрутизировался внутрь себя.
- Маршруты зарубежного egress не имеют fallback на main RU; дополнительные правила форвардинга не допускают egress-mark → RU WAN.
- Ограничить доступ клиентов к management networks, docker bridges и приватным адресам за исключением согласованных сервисов (например, локальный DNS).
- Обе VPS поддерживают возможность аварийного восстановления через панель хостинга/serial console; изменение firewall только после проверки rollback-канала.
- Для IPv6 не выдавать клиентам IPv6 и исключить клиентские утечки, но не ломать IPv6 существующего FR сервиса.

## 6.1. Смена зарубежного endpoint и замена узла

- `/etc/hosts` на RU — **кандидат**, не утверждённый способ смены IP зарубежного egress, не публичный реестр. Менять только конкретную управляемую запись, не перезаписывать весь файл. Резервная копия, атомарное применение, контроль прав и запись в аудит.
- Проверить разрешённый IP до применения к выбранному транспорту. После применения проверить не только handshake, но и внешний IP; при отказе зарубежный трафик остаётся fail-closed. Не выполнять автоматический fallback через RU.
- При полной смене зарубежного узла новый узел должен предъявлять ожидаемый публичный ключ межсерверного пира (либо ключ обновляется на RU согласованной операцией); отсутствие криптографической идентичности нельзя компенсировать только hostname.
- Секреты/ключи зарубежного узла не передавать через бота или plaintext бэкапы; проверить безопасный перенос и уничтожение копий. Изменение действующего Docker/AmneziaVPN без отдельного owner approval запрещено; планового удаления нет.

## 7. Резервные копии

- Локальная копия + **зашифрованная** копия вне RU на выбранном защищённом узле/носителе (FR — лишь кандидат после оценки рисков, без зависимости от рабочего Docker VPN). При смене зарубежной VPS backup-приёмник и тест восстановления переносить осознанно: резервная копия не должна оставаться исключительно на выведенном узле.
- Включить SQLite consistency, конфиги, ключи и данные для воспроизводимого восстановления; контролировать права на архивы.
- Ключ расшифрования не хранить только на том же зарубежном диске рядом с копией. Продумать оффлайн-восстановление без Telegram.
- Периодически проверять реальное восстановление на тестовом окружении.

## 8. Аудит и реагирование

- Учитывать создание/отзыв ключей, смену лимитов, одобрения, удаление, административные роли, откаты и изменение маршрутов.
- Отдельный алерт о недоступности egress, неисправном egress, старении IP-списков, опасной загрузке диска, ошибке копирования, невозможности получить метрики, смене IP зарубежного узла/endpoint и несоответствии фактического зарубежного egress ожидаемому.
- При недоступности Telegram сохранить события локально и повторить доставку после восстановления, избегая лавины одинаковых сообщений.

## 8.1. Административный доступ Codex (2026-11-07)

- Проверенный SSH: `vpn-ru` / `vpn-fr`, пользователь `wolffrog`, отдельные Ed25519-ключи `codex_ru` / `codex_fr`; **не** являются Deploy Keys GitHub.
- Только read-only аудит без специального разрешения на системные изменения. `sudo -n -l` запрашивает пароль; отсутствие passwordless sudo не обходить и не заменять `NOPASSWD: ALL`.
- Политика auto-approval Codex и аутентификация SSH независимы. Отмена сохранённых Codex rules **не** отзывает серверные SSH-ключи. Отзыв прав входа требует удаления ключа с каждой VPS; активные сессии надо завершать отдельно.
- Секреты не копировать из хостов, Docker environment, конфигураций VPN и логов в чат/репозиторий.

## 9. Запреты исполнителю

Никаких действий с публичными маршрутами, UFW, nftables, iptables, `sysctl`, Docker, DNS или SSH production без явно разрешённого этапа, проверенного recovery-канала и созданного бэкапа. Никогда не просить вставить приватный SSH-ключ, root-пароль или bot token в обычный чат.
