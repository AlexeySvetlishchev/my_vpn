# WORK_RULES — контракт для исполнителя (Work/Codex/человек)

## 0. Источник истины

Сначала прочитать `README.md`, `SPEC.md`, `SECURITY.md`, `DECISIONS.md`, `ARCHITECTURE.md`, `ACCEPTANCE.md`. Все согласованные требования уже приняты. **Не строить новую архитектуру** в ответ на широкий промпт и не подменять решения «более рекомендуемыми» технологиями.

## 1. Каждая задача имеет границы

Перед работой исполнитель фиксирует: цель, входные данные, доступные инструменты, требуемые права, затрагиваемые серверы, перечень разрешённых изменений, запрещённые действия, проверку успешности и rollback. Если нет доступа/исходных данных — статус `BLOCKED`; не симулировать аудит.

Не запускать ресерч, генерацию файлов, команды или установку, если конкретное узкое задание ограничено проверкой наличия доступа.

## 2. Четыре типа действий

- `READ_ONLY`: просмотр разрешённых настроек, без скачивания/публикации секретов и без изменения состояния.
- `LOCAL_BUILD`: написание/тестирование кода офлайн, без доступа к production.
- `STAGING_CHANGE`: изменения только в тестовом окружении.
- `PRODUCTION_CHANGE`: только после явного согласования владельцем конкретной операции, бэкапа и плана rollback.

Переход от READ_ONLY к PRODUCTION_CHANGE никогда не подразумевается автоматически.

## 3. Отчёт не должен выходить за пределы фактов

Разделять:

- `Observed` — реальные факты из инструментов, команды, временные метки и результаты.
- `Inferred` — предположения и их степень уверенности.
- `Proposed` — ещё не реализованные действия.
- `Blocked` — неизвестное или невозможное без доступа.

Если не получены IP/SSH/разрешения, писать «аудит не выполнен», а не выдавать исследование документации за аудит.

## 4. Обязательные стоп-условия

Остановиться и запросить согласование, если необходимо:

- менять утверждённые требования;
- трогать действующую NL AmneziaVPN/Docker **до отдельной разрешённой финальной операции удаления**;
- заменять AWG другой технологией или требовать клиентский Telegram;
- изменять default route, SSH-доступ, глобальный firewall, NAT или IPv6 хоста;
- вводить новый сервис, существенно увеличивающий нагрузку;
- выполнять операции без проверяемого rollback или консоли провайдера.

## 4.1. Специальные правила переключения NL

Смена публичного IP NL допустима только в согласованном `PRODUCTION_CHANGE` (или staging-тесте). Исполнитель не подменяет клиентские конфиги AWG, не меняет публичную точку входа RU, не подставляет новый ключ WG-пира без согласования. Запись в `/etc/hosts` сама по себе не является успешным переключением: подтвердить активный WireGuard endpoint и фактический egress, сохранить fail-closed. При замене всей NL VPS — предварительно обеспечить WG identity, NAT, маршруты, firewall, бэкапы и rollback.

Удаление прежней NL AmneziaVPN/Docker **обязательно в целевом состоянии, но запрещено до явного отдельного утверждения**, после успешной приёмки новой системы.

## 5. Секреты и доступ

Не требовать пароли/root SSH keys/bot token в чате. Использовать штатный разрешённый механизм передачи секретов с минимальными временными полномочиями. Не открывать административный HTTP API в интернет. Секреты — локальные файлы с ограниченными правами/секрет-хранилище, никогда — коммит.

## 6. Формат каждого результата

1. Цель и scope.
2. Что было доступно и что реально выполнено.
3. Таблица фактов/проверок.
4. Изменённые файлы/системы (или «ничего не менялось»).
5. Отклонения от SPEC: только в виде предложения, не реализованные.
6. Риски, тесты и способ отката.
7. Одно точное следующее действие и требуемое разрешение.

## 7. Практическое правило

Общий текст «построй VPN RU → NL» **запрещён** как автономная команда на исполнение. Использовать узкие `TASK_*.md` с чётким scope. Work не должен расходовать ресурсы на повторное проектирование уже согласованной системы.
