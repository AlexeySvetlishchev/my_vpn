# NL_ENDPOINT_RUNBOOK — смена IPv4 и замена NL VPS

**Статус:** регламент для будущей реализации; команды `vpnctl` ниже — проектируемые, не существующие. Выполнение в production — только после отдельного разрешения, аудита и бэкапа. `nl-egress.internal` и IP `203.0.113.10` — примеры, не реальные адреса.

## Цель и границы

Публичный IPv4 NL часто меняется. Клиенты продолжают подключаться к RU по AmneziaWG с прежними файлами вида `Ivan_iPhone.conf`. NL остаётся **egress**, а не клиентским endpoint. Переключение NL не меняет IP/ключи/профили AWG на RU.

## Единая точка задания адреса

На RU межсерверный WireGuard конфиг содержит `Endpoint = nl-egress.internal:51820` (порт примерный). Локальный `/etc/hosts` RU содержит ровно одну управляемую запись hostname → IPv4, например `203.0.113.10 nl-egress.internal`. Проверить разрешение через `getent ahostsv4 nl-egress.internal`. Локальная запись не требует публичного DNS.

**Предупреждение:** Linux/WireGuard не обязан автоматически повторно разрешать имя после редактирования `/etc/hosts`. Для действующего пира нужен явный `wg set <interface> peer <public-key> endpoint <hostname>:<port>` или эквивалентное обновление через локальный менеджер. Не перезапускать клиентский AWG.

## Смена IP на той же VPS

1. До изменения: выяснить текущий endpoint, ключ пира и работоспособность; получить точный новый IPv4 у провайдера и проверить его привязку к NL. Сделать резервную копию управляемого файла и состояния верификации без экспорта приватных ключей в отчёт.
2. Проверить, что `NEW_IP` — допустимый публичный IPv4, что совпадает ожидаемая страна egress, что нужный UDP-порт доступен и что новая NL готова отправлять трафик.
3. Под блокировкой от параллельного обновления атомарно изменить **только** управляемую запись `nl-egress.internal` в `/etc/hosts` RU, сохранив все остальные записи.
4. Повторно разрешить hostname; применить `wg set` к рабочему peer; проверить `wg show ... endpoints`, handshake, обмен байтами и **фактический интернет-egress с новой NL**, а не только успешность команды.
5. При успехе: зафиксировать новое значение и результаты, алерт/аудит. При неудаче: вернуть прежнюю запись и прежний активный endpoint, **только если старый endpoint реально доступен**; иначе сохранить блокировку NL-трафика и зарегистрировать отказ. Никогда не переключать NL-трафик на RU WAN.
6. Проверить восстановление после перезагрузки RU: WG поднимается с hostname, `/etc/hosts` резолвится до поднятия интерфейса, активная и файловая конфигурации согласованы.

## Замена всей NL VPS

1. Развернуть новую Ubuntu 24.04 NL в отдельном согласованном окружении, без зависимости от старых Docker/AmneziaVPN контейнеров.
2. Установить минимальные WG, ip forwarding, адреса туннеля, обратный маршрут к клиентской сети, scoped firewall/NAT, диагностику и приём зашифрованных резервных копий.
3. Перенести WG private key NL **только через безопасный секретный канал** и с контролем прав, если должна сохраниться прежняя криптографическая идентичность. Альтернатива — создать новый WG keypair и отдельным согласованным действием заменить peer public key на RU. Смена IP **не подразумевает** автоматической смены ключа.
4. Проверить NL без переключения production: WG-порт, маршрут, NAT, реальный внешний IPv4, health-check, восстановление резервных копий. Использовать тестовый туннель/период переключения по согласованному плану.
5. Переключить локальный hostname на RU и активный WG endpoint; проверить fail-closed и фактический egress. Состояние RU AWG и клиентские конфигурации не менять.
6. Старую VPS выводить из эксплуатации отдельно, после фиксации успешных тестов, и убедиться, что зашифрованные бэкапы доступны на новой точке.

## Права и журналирование

`vpnctl nl set-ip NEW_IP` (проектируемый CLI) выполняется только Owner/Admin через привилегированный локальный helper. Telegram — опциональный адаптер к той же операции, не самостоятельный источник конфигурации. Нужны повторяемость, блокировка гонок, backup/rollback, запись кто/когда/с какого IPv4 на какой/результат (без ключей).

## Критерии успешности

- Клиенты не получают новые `.conf`, AWG RU не перезапускается.
- Текущий активный WG endpoint соответствует ожидаемому новому IPv4.
- Реальный внешний IPv4 для тестового NL-потока = проверенный адрес новой NL.
- RU-потоки продолжают работать напрямую.
- При сбое изменения нет маршрута NL → RU; rollback либо явный fail-closed.
- Конфигурация переживает reboot и не зависит от Telegram.
