# TASK 02 — подготовка RU после установки AmneziaWG

Scope разработки: **LOCAL_BUILD**, без SSH, commit и push. Создание скрипта
не разрешает его выполнение на production. Предыдущий TASK_01 завершён по
сообщению владельца; текущее узкое задание задано его новым запросом.

Вход со слов владельца: Ubuntu 24.04, ядро 6.8.0-147-generic, пользователь
wolffrog с sudo; AWG установлен, модуль загружается, доступны awg/awg-quick,
wg/wg-quick, nft, tc; репозиторий клонирован read-only Deploy Key.
Это не результаты нового удалённого аудита исполнителя.

## Точный набор предлагаемых изменений

После отдельного одобрения `--apply` создаёт только отсутствующие объекты:

| Путь на RU | Владелец / права | Назначение |
|---|---|---|
| `/etc/amnezia` | root:root / 0755 (новый); 0755 или 0700 (существующий) | Родитель каталога AWG |
| `/etc/amnezia/amneziawg` | root:root / 0700 | Каталог будущей конфигурации AWG |
| `/etc/wireguard` | root:root / 0700 | Каталог будущей конфигурации WG |
| `/etc/amnezia/amneziawg/awg0.conf.template` | root:root / 0600 | Неактивный AWG-шаблон |
| `/etc/wireguard/wg-nl.conf.template` | root:root / 0600 | Неактивный шаблон RU → NL |

Пути — выбор реализации этого подготовительного этапа. Шаблоны не являются
готовыми production-конфигами. Активные `.conf` не читаются и не изменяются.
Существующие каталоги должны уже иметь указанные права; скрипт не исправляет их.
Существующий `/etc/amnezia` root:root с 0755 или 0700 сохраняется без изменений;
новый создаётся с 0755. Для `/etc/amnezia/amneziawg` и `/etc/wireguard`
по-прежнему обязательны root:root и 0700, для шаблонов — root:root и 0600.
Существующие шаблоны сохраняются, если совпадают содержимое и метаданные;
при отличиях скрипт прекращает работу до записи. Ссылки и небезопасные
родительские каталоги отклоняются. Запускать только из проверенной копии
репозитория, без параллельного редактирования целевых путей.

Проверки: Ubuntu 24.04, root, наличие утилит (включая `modinfo`), установленный
AWG-модуль для текущего ядра через `modinfo amneziawg`,
успешные `awg show interfaces` и `wg show interfaces` без интерфейсов
в текущем network namespace. Ядро выводится, но не закрепляется за одной
patch-версией. Наличие `/sys/module/amneziawg` не требуется; AWG- и WG-модули
автоматически не загружаются. При отсутствии `modinfo` или ошибке проверки
модуля скрипт завершается с ERROR и кодом 1 до любых записей.
Наличие утилит и успешный `modinfo` не доказывают
их совместимость или работоспособность VPN; внешний egress не проверяется.

Нет установки пакетов, Docker, генерации ключей, изменения `/etc/hosts`,
firewall, маршрутов, sysctl, SSH, служб или автозапуска. Dry-run не создаёт
даже временных файлов. В apply временный файл 0600 создаётся рядом с целью
и публикуется без перезаписи существующего пути.

## Запуск владельцем на RU

Из корня проверенной копии репозитория:

```bash
bash -n scripts/02_ru_prepare.sh
bash scripts/02_ru_prepare.sh --help
sudo bash scripts/02_ru_prepare.sh --dry-run
```

Без аргументов действует dry-run. Проверка требует sudo и ничего не меняет
в конфигурации; сам sudo может оставить штатную запись аудита системы.
Ошибки имеют префикс ERROR, код 1; неверные аргументы — код 2.
Отсутствующие зависимости не устанавливаются автоматически.

Только после одобрения точного набора выше, резервирования и плана отката:

```bash
sudo bash scripts/02_ru_prepare.sh --apply
sudo bash scripts/02_ru_prepare.sh --dry-run
```

Второй запуск должен показать только KEEP и DONE. Повторный `--apply`
должен также показать KEEP без изменения содержимого, прав и mtime.
Вывод CREATED сохранить вне Git для точного отката. Никаких ключей или
конфигураций с секретами в репозиторий не добавлять и не выводить в чат.

## Проверки синтаксиса и ограничения

Локальная регрессия: `bash tests/02_ru_prepare_test.sh`. Проверяет допустимые
и недопустимые метаданные каталогов/шаблонов и отсутствие записей в dry-run.
Тест исполняет файловую часть скрипта на временных фикстурах с подменой `stat`;
проверки Ubuntu/root/модуля не исполняются. Это не проверка на Ubuntu/VPS.
Символические ссылки проверяются, если локальная файловая система поддерживает
их создание; иначе тест явно сообщает SKIP. `--apply` не запускается.

`bash -n` проверяет синтаксис скрипта без исполнения. `--help` безопасен
без root. Полный dry-run на RU проверяет условия, но не синтаксис будущего
production AWG/WG-конфига: плейсхолдеры намеренно невалидны для активации.
Не использовать `awg-quick up`, `wg-quick up`, `setconf` для проверки шаблонов.
Параметры AWG, подсети, MTU, порты и hostname требуют отдельной проверки/решения;
не переносить примерные адреса из ARCHITECTURE как утверждённые значения.

Этот этап не реализует fail-closed и не закрывает приёмку этапов 2–3 из
ACCEPTANCE.md: до активации нужны отдельные PBR/firewall/IPv6/DNS-проверки.

## Резервирование, риски, откат

Перед production apply сохранить snapshot VPS средствами провайдера и
список существовавших целевых путей/метаданных вне Git, проверить доступ
к консоли восстановления. Содержимое существующих VPN-конфигов не печатать.
Перезаписи нет, поэтому файловый backup секретов этим скриптом не создаётся.

При ошибке записи возможен частично подготовленный набор каталогов/шаблонов;
повтор безопасен для полностью созданных совпадающих файлов. При аварийном
завершении может остаться `.ru-prepare.*` без секретов — проверить вручную.
Откат по журналу CREATED: удалить только созданные данным запуском шаблоны,
предварительно подтвердив, что они всё ещё совпадают с исходными и не были
использованы/изменены; затем удалить только созданные пустые каталоги через
`rmdir` в обратном порядке. Существовавшие объекты не удалять. Рекурсивное
удаление каталогов VPN запрещено. Откат сети/служб этому этапу не требуется.

Следующее действие: ревью этих четырёх файлов владельцем; запуск на VPS
и публикация изменений выполняются только по отдельному подтверждению.
