# SPEC — VPN RU → NL

Версия baseline: 1.1 · 2026-11-03 · проектная спецификация на основе согласованных требований.

> **Статус:** документ подготовлен к утверждению владельцем. Пункты со статусом «УТВЕРЖДЕНО» отражают договорённости; это не означает, что система уже развернута.

## 1. Цель и масштаб

**УТВЕРЖДЕНО.** Построить легковесную инфраструктуру для порядка 10–50 VPN-клиентов с единой точкой подключения в РФ, автоматическим выбором страны выхода и независимым управлением. Приоритеты: практическое удобство человека, сохранение безопасности и существующего сервиса, минимальное потребление ресурсов.

Две VPS: Ubuntu 24.04 LTS, каждая 2 vCPU и 4 ГБ RAM. VPS РФ чистая. VPS NL в момент внедрения эксплуатируется: на ней работает AmneziaVPN в Docker. **До переключения на новую production-систему действующую установку сохраняем**, не останавливая и не нарушая её работу. **После приёмки новой системы старую AmneziaVPN и связанные с ней контейнеры/остаточные компоненты полностью удаляем отдельной согласованной операцией.** В целевой схеме старых контейнеров нет.

## 2. Передача трафика

- **УТВЕРЖДЕНО.** Клиенты подключаются к VPS РФ по **AmneziaWG**; приложение на устройстве может быть совместимым клиентом AmneziaVPN/AmneziaWG.
- **УТВЕРЖДЕНО.** Российские IP-назначения выходят напрямую с IP VPS РФ; остальные публичные IPv4 — через туннель к VPS NL и выходят с IP VPS NL.
- **УТВЕРЖДЕНО.** Поддерживаются администраторские исключения для принудительного направления выбранных IP/CIDR через NL.
- **УТВЕРЖДЕНО.** При отказе NL трафик, отнесённый к NL, блокируется; **аварийного выхода через РФ нет**. Российский прямой выход должен сохраняться, если RU доступен.
- **УТВЕРЖДЕНО.** Межсерверное соединение — обычный WireGuard; IPv6 для VPN-клиентов отсутствует в первой версии. Это не даёт разрешения отключить IPv6 хоста и нарушить его действующие сервисы.
- **УТВЕРЖДЕНО.** Один лёгкий DNS-резолвер/форвардер для клиентов на VPS РФ; географически раздельный DNS не входит в первый этап.
- **УТВЕРЖДЕНО.** Списки российских сетей и исключений обновляются автоматически ориентировочно каждые 12 часов; ошибка обновления не должна уничтожать предыдущую рабочую конфигурацию.

## 2.1. Заменяемая NL VPS и смена адреса

- **УТВЕРЖДЕНО.** Публичный IPv4 NL может часто меняться, и такая смена является штатной операцией эксплуатации, доступной через `vpnctl` и администраторский интерфейс Telegram. Сам туннель и клиентские профили РФ должны переживать смену адреса без переиздания клиентских `.conf`.
- **УТВЕРЖДЕНО.** На RU endpoint межсерверного WireGuard задаётся **стабильным hostname**, пример `nl-egress.internal`; его IPv4 разрешается локально через `/etc/hosts` на RU, без обязательного публичного DNS или API провайдера.
- **УТВЕРЖДЕНО.** Изменения `/etc/hosts` недостаточно для уже запущенного WireGuard: менеджер должен явно обновить активный endpoint пира, проверить handshake и фактический egress через NL; при ошибке — fail-closed и безопасный откат, без выхода NL-трафика через RU.
- **УТВЕРЖДЕНО.** Допускается замена всей NL VPS: развернуть новую точку из воспроизводимой минимальной конфигурации и перенести/согласованно заменить межсерверные WG-ключи. Новая NL должна иметь правильный маршрут к клиентской подсети, NAT и firewall. Клиентские AWG-конфигурации **не меняются**.
- **ПРОВЕРИТЬ.** Конкретные команды `wg set`, поведение resolver (`/etc/nsswitch.conf`, `getent`), наличие конфликта имён, проверка живого endpoint, сценарий отката и применение конфигурации после reboot. Само изменение `/etc/hosts` не обеспечивает динамическое переподключение.

## 3. Пользователи и профили

- **УТВЕРЖДЕНО.** Пользователя создаёт администратор вручную либо через одобрение заявки, принятой через разрешённый интерфейс.
- **УТВЕРЖДЕНО.** Имя вводит человек. Если создан `Ivan`, то в CLI, боте, статистике и списках пользователь отображается **Ivan**, а не `user_001` или UUID.
- **УТВЕРЖДЕНО.** Имена пользователей уникальны без учёта регистра. При конфликте понятная ошибка и повторный выбор имени. Отображаемый регистр исходного имени сохраняется.
- **УТВЕРЖДЕНО.** Один пользователь может иметь несколько независимых VPN-аккаунтов/профилей — по одному на устройство. Каждый имеет собственные ключи, назначенный VPN IP, статус, лимиты скорости и статистику.
- **УТВЕРЖДЕНО.** Стандарт имени профиля и выдаваемого файла: `ИмяПользователя_ИмяУстройства` (подчёркивание, **не дефис**), например `Ivan_iPhone.conf`, `Ivan_MacBook.conf`. Имена устройств уникальны в пределах пользователя.
- **УТВЕРЖДЕНО.** Телефон, email, Telegram ID и прочие внешние идентификаторы **не являются обязательными полями пользователя или VPN-аккаунта**. Пользователь VPN может вообще не иметь Telegram.
- **УТВЕРЖДЕНО.** Администратор способен создавать и обслуживать пользователя без Telegram у получателя, получая конфигурацию для внешней передачи.
- **УТВЕРЖДЕНО.** Обычный пользователь не может менять лимиты скорости; лимиты назначает и меняет только администратор.
- **ПРОВЕРИТЬ.** Точное отображение названия после импорта в каждое целевое приложение; не обещать, что все версии клиента автоматически применят имя файла.
- **ОТКРЫТО.** Допустимый набор символов пользовательского имени и имени устройства, политика переименования, число устройств на одного пользователя и значения лимитов по умолчанию. Составные имена не должны ошибочно разбираться по символу `_`; в модели пользователя и устройства имена хранятся раздельно.

## 4. Управление — без зависимости от Telegram

- **УТВЕРЖДЕНО.** Ядро: локальный VPN Manager; самостоятельный CLI является обязательным рабочим интерфейсом. Telegram — **опциональный адаптер** к тому же менеджеру, не источник истины.
- **УТВЕРЖДЕНО.** Прекращение работы Telegram/бота не прерывает существующие VPN-сессии, NAT, PBR, лимиты и сбор базовых метрик.
- **УТВЕРЖДЕНО.** CLI должен поддерживать создание, просмотр, блокировку пользователей/профилей, выдачу конфигураций, изменение скорости, получение состояния и статистики.
- **УТВЕРЖДЕНО.** Для Telegram-приёма заявок: строго одноразовое приглашение → заявка → одобрение уполномоченным администратором. Неавторизованные лица не получают административных возможностей или сведений об инфраструктуре.
- **УТВЕРЖДЕНО.** В Telegram администратор также может вручную создать пользователя и несколько профилей для человека без Telegram. Административные действия имеют ролевую модель Owner/Admin/User.
- **ОТКРЫТО.** Как пользователь без Telegram безопасно получает и обновляет секретный конфиг: локальная выдача администратору и внешний канал либо одноразовый защищённый портал; выбрать после анализа рисков.

## 5. Ограничения скорости и мониторинг

- **УТВЕРЖДЕНО.** Индивидуальные ограничения скорости на профили/устройства, задаваемые администратором; сохраняются после перезагрузок и не обходятся сменой страны выхода.
- **УТВЕРЖДЕНО.** Статистика отдельно по профилю, агрегированная по пользователю; при необходимости — RU/NL и ресурсы обеих VPS.
- **УТВЕРЖДЕНО.** Бот выполняет роль дашборда с графиками за разные интервалы, а также отправляет аварийные уведомления. CLI не зависит от бота и обеспечивает просмотр состояния.
- **УТВЕРЖДЕНО.** Система лёгкая: не развертываем Grafana, Prometheus, FRR, BIRD, ExaBGP и отдельную серверную БД без доказанной необходимости.
- **ПРОВЕРИТЬ.** Конкретная схема `tc` для отдельных направлений download/upload, способы надёжного учёта по AWG-пиру, точность измерений, стоимость хранения временных рядов.

## 6. Резервирование и эксплуатация

- **УТВЕРЖДЕНО.** Локальные резервные копии на RU плюс зашифрованная копия на NL. Восстановление возможно без Telegram.
- **УТВЕРЖДЕНО.** Во время внедрения действующая AmneziaVPN на NL должна сохраниться в рабочем состоянии. Нельзя делать `flush ruleset`, бездумно заменять политику firewall или default route, отключать Docker либо занятые порты. **После приёмки нового production** следует отдельно согласованное полное выведение старого Docker/AmneziaVPN из эксплуатации с проверкой, что не удалены общие зависимости новой системы.
- **УТВЕРЖДЕНО.** Для RU и NL предусмотрены автостарт сервисов, диагностика и проверяемый откат; секреты не публикуются в чат, код и отчёты.

## 7. Границы решения

Не входят в первый этап: BGP, внешние веб-панели, обязательная учётка Telegram, клиентский IPv6, автоматическая миграция существующих пользователей AmneziaVPN NL, биллинг, сложная многоузловая HA-схема. **Вывод старой NL AmneziaVPN из эксплуатации входит в проект как заключительная миграционная задача, но не в ранние этапы.**

## 8. Порядок работ

1. Проверить возможности инструмента исполнителя, потом **read-only** аудит RU и NL.
2. Установить и проверить AmneziaWG на RU (пока локальный выход RU).
3. Развернуть отдельный WireGuard RU↔NL и split routing с fail-closed, не затрагивая старый AmneziaVPN NL.
4. Реализовать VPN Manager, SQLite, CLI, правила имён, устройства, скорость.
5. Подключить Telegram-адаптер, приглашения, одобрение, дашборд и алерты.
6. Испытать рестарты, отказ NL, восстановление из резервной копии, нагрузку и совместимость существующего NL VPN; проверить смену публичного IP NL и замену VPS без переиздания клиентских конфигов.
7. После подтверждённого запуска новой production-системы отдельным разрешённым этапом завершить эксплуатацию прежней NL AmneziaVPN/Docker, удалить её компоненты и проверить сохранение работоспособности нового туннеля. См. `NL_MIGRATION.md`.

**Каждый этап — отдельное поручение и отдельное разрешение на изменения.**
